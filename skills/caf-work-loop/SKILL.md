# Caf work loop

Keep the owner's Cafetera and Caffeine backlogs moving toward the vision in AGENTS.md without supervision, one verified task at a time, while every decision that belongs to the owner waits for the owner.

## Run the unattended Caf work loop

This skill holds the loop procedures. Two records own the rules. The operating-loop rule `caf:agentspec:rule:agent-operating-loop` owns the steps and the stop for one task. The session record `caf:agentspec:loop:cafetera-main` owns the goal epic, the journal task, the limits, the order rule, the must-nots, the stop conditions, and dated overrides. `caf situation` prints the record's main effective values for the owner's local date on its `Loop:` line and the goal epic on its `Plan:` line. The loop prompt only names the record. When the owner changes a session rule in chat, obey it for the date that the owner names, journal it, and prepare a dated override row in the record for the owner to accept. You can adopt a tighter limit or an extra stop yourself; journal it, and keep it reversible.

The sections map to the steps of the rule: Choose one task is orient and find; Do the work is propose, preflight, and execute; Review, verify, commit, and push is observe and decide; Park is decide for owner-reserved cases; Stop and report is crystallize. Recover applies at every step.

### Choose one task

1. From Cafetera, list ready and in-progress work for every lane of the record with `caf task ready --lane all` and `caf task list --lane all --status in_progress`. Each row starts with its lane name, and each lane is read through its own Beads route. Read each repository's own `AGENTS.md` before working in it. When a lane prints `not read`, follow the fix it names, such as `BEADS_ACTOR=<your agent id> caf workspace bind --linked-root caffeine=PATH` with the Caffeine checkout; its native fallback is `bd ready` in that lane's checkout. Claims, comments, and closes always run in the lane's own checkout, never through a lane.
2. Take the task order from Beads only, as the record's order rule says. Prefer finishing an in-progress task assigned to this agent. Otherwise take the ready task under the goal epic, an epic related to it in Beads, or the journal task, by priority, then lower milestone, then age, that is unassigned or assigned to this agent's role. Until Narrow passes, take at most 1 self-improvement task (one that improves Caf's own loop, guidance, or tools) for each 2 goal tasks. Work in the record's lanes: each lane takes its order from its own Beads database and writes as its own agent id, such as `caffeine-agent`. A lane with a minimum share gets it while it has ready work; an unused share returns to the other lanes, and every task of a lane without a goal epic counts as a goal task.
3. A task assigned to another agent role is eligible only when all three hold: the owner asked for that workstream, its Beads history shows no update in the last 24 hours, and no live session is updating it. Check the Beads comments and, for Caf work, `caf activity list --task <id>`.
4. Confirm the work is still needed against current source, history, tests, and open reviews before you claim or take over a task. Write task comments, notes, and closes with `caf task comment <id> --file FILE`, `caf task note <id> --file FILE`, and `caf task close <id> --reason-file FILE --evidence RUN`. They record the agent that your session names. At the start of each session, write one start note: `BEADS_ACTOR=<your configured agent> caf note --task <journal task> --kind intent --target caf:coordination:agent:<your configured agent> --text 'Session start'`. Every later `caf` command of that session in that workspace then carries your agent, reads included; `caf situation` prints the exact line when it is missing. A helper never writes a start note; it keeps `BEADS_ACTOR=<its delegate id>` on each command. Use `bd` only for writes that `caf task` does not have yet, such as claim, take-over, and create, and for recovery when `caf task` fails. Pass `bd --actor <your agent id>` on every such Beads write. Without it, Beads records the Git user name, which is a person, not an agent. Do not rely on `export BEADS_ACTOR=<your agent id>` alone: Claude Code runs each command in a new shell, so the export is lost after one command. Claim an unassigned task or a task of your own with `bd --actor <your agent id> update <id> --claim`.
5. To take over an eligible task, run `bd --actor <your agent id> update <id> --assignee <your agent id>`; a comment alone leaves the old owner in `bd ready`. Write one comment with `caf task comment <id> --file FILE` that gives: the previous owner and their last update date; the branch and commits you reuse; the items you leave untouched; the checks already run; the open questions (`caf:agentspec:rule:cafetera-agent:exact-cross-repository-handoff`). Write one journal note. Then claim it with `bd --actor <your agent id> update <id> --claim`.

### Do the work

Follow the repository's `AGENTS.md`: CML first, a failing test first, the smallest complete change, beginner-readable HxDoc, and the repository formatter. Record failed reuse and new gaps as Beads tasks instead of widening the current task, within the record's self-improvement ratio. Before you write code, find the module that owns the meaning of each new piece and the pattern that joins it, and put the piece there (`caf describe caf:concept:statement:semantic-tree:module-fit`). A temporary home needs a filed task that moves the piece.

For every step, find the existing Caf piece first and use it (`caf:agentspec:rule:caf-knowledge-first`). When none fits, extend Caf with the smallest piece at the right rung on a branch, with tests and the run that needed it (`caf:agentspec:rule:scoped-self-extension`). Turn each friction into a Caf default, such as refusal text, a `Next:` hint, a default record, or a task under the friction epic `cafetera-0jpj`. Never keep it only in a memory file (`caf:agentspec:rule:owner-prompt-to-default`). Sometimes you find a component, rule, command, record, or habit that works against the Caf vision (`caf:concept:model:caf-first-principles-v0` and `AGENTS.md`). Examples are a second authority, ceremony that does not pay rent, a confusing surface, or a part that no consumer uses. Record one task under the friction epic with the evidence, even when it is outside your task. Then write one journal note of kind question that names the task as a vision gap, so the next progress report lists it under the challenges. Do not fix it inside your current task. Take business facts from CML records and defaults; do not ask the owner for them.

When a task changes what a person sees, add or update one small scenario in the same task. A scenario has about ten expectations, each one visible outcome, with no paths, digests, tasks, or status. Put each change to scenario text or to a bound test in its own named commit. Bind each new expectation to a hand-written browser test through one check record. Run the scenario check, such as `pnpm check:scenarios` in Caffeine, before review and on each UX integration's gate commit, and publish its report. A new place, navigation model, or outward surface starts outside-in: first a mockup and failing checks, then the code. It waits until the owner accepts the mockup.

For a native tool such as Beads, git, Haxe, `caf-oracle`, Playwright, or pnpm, use the one write route that `caf describe caf:concept:statement:semantic-tree:tool-routes` names; reads may use either route.

Journal every decision, review verdict, worker handoff, merge, and friction with `caf note --task <loop epic>` (`caf:agentspec:rule:loop-journal`). Keep each long report, such as a review, at `.caf/evidence/<loop epic>/<sha256>.md`, and name that digest in the note. Journal each decision with `--follow-up ID`, an open task of this repository that carries the follow-up work, or `--no-follow-up REASON` when no work follows; `caf note` refuses a decision with neither. Pass `--target ID` with each decision to name the record it governs, and write its Concept statement in that record's model (`caf:concept:statement:principle:every-act-names-its-record`); when it governs no record, say why in `--text`. Back-fill an older decision with one new note per decision that passes `--corrects BLOCK`. Before you pick work, run `caf situation --full`; when it reports decisions without a follow-up task, or follow-up tasks not reachable by `bd ready`, fix those first.

Notice work that you repeat by hand, so that it can move into CML. At the end of each task, look for a sequence of steps that you ran by hand and that an earlier task also needed. The second time, write one `caf note --kind claim` that names the sequence, with `--target` set to the `caf:` id of its existing owner, such as `caf:task:beads:ID` for a Beads task. Before you propose, find the earlier claim note with `caf note list --task <loop epic>`. The third time, propose the smallest CML step that extends that owner, as one Beads task, and do not activate it. Propose only when all of these are true: the sequence has at least three steps in a stable order, it repeated across at least two tasks, an existing owner fits, and you can name the benefit, such as an earlier failure, fewer owner prompts, or recovery. When the owner declines a proposal, record that as a `caf note --kind decision --no-follow-up REASON` and in the task, so that nobody raises it again.

At session start, `./bin/caf situation` prints the workspace, the selected policies, the catalog commands, and the loop facts in a few seconds; it defers the open focus tasks and the pickup counts to `caf situation --full`. Take the loop goal from its `Plan:` line, the main limits and must-nots from its `Loop:` line, and all limits from the `caf describe` page that the `Loop:` line names. Take the task order from Beads.

Before you use a `caf` command, run `./bin/caf help --json` in Cafetera. It prints one JSON catalog of every command path with its purpose, options, examples, mode, actions, and declared effects. Do not guess commands or flags. The catalog grants no effect; the host's effect policy still decides each run.

Before you write CML, run `./bin/caf help cml`: it first shows which tag to start with for a request such as a skill, a KB note, a workspace, a CLI command, or an approval, where the file goes, and which worked example to read, then lists every tag. Run `./bin/caf help cml <tag>` to see the tag's attributes and types, enum values in the `{Enum.Value}` form, what goes inside it, which tags it fits inside, and its worked example; `--json` prints the whole catalog. Do not guess tags or attributes.

### Review, verify, commit, and push

1. Workers run only the focused lanes for what they changed. After a merge of the main branch that changes only pins, run `./bin/update-pins --check` and the affected lanes.
2. Each task that changes source gets one review by the independent reviewer on its exact commit, then its fixes (`caf:agentspec:rule:review-gate-and-stop`). Each review brief asks the reviewer to apply `caf:concept:statement:independent-review:cml-route-check` and `caf:concept:statement:independent-review:module-fit-check`. A task gets at most 3 review rounds (the record's review cap); after the third, get a second opinion or park the task. A pure Beads export refresh or pin refresh gets no review. When the task changes what a person sees, the review names the scenario and its check record. It also holds screenshots at 390 and 1440 px beside the accepted mockup and answers the six review questions of `caf:agentspec:rule:ui-quality`. Start the verdict note with the verdict (approved, changes requested, or inconclusive) and the commit. For the reported level on line 2 of the verdict, a reviewer on Claude Code reads the `CLAUDE_EFFORT` environment variable in its own shell; it writes `unknown` only when that variable is not set.
3. The coordinator integrates one task at a time: merge the pushed worker branch into the local main branch with a merge commit. Never rebase, squash, or cherry-pick it, so that git can prove what landed (owner decision WT2, 2026-11-16). In Cafetera, do not merge by hand: give each approved branch to `./bin/land --merge BRANCH` (step 4). It merges after its checks and before it rebuilds the CLI, which also binds the checkout again, so `caf note` keeps working after a merge that changes `caf/Workspace.hx`. On a conflict it changes nothing. Integrate no more tasks a day than the `Loop:` line allows. Use the gate train (owner decision 2026-11-10): stack up to 3 reviewed tasks on the main branch, then run one complete gate on the tip commit. When it passes, it covers each task in the train. When it fails, gate each task alone on its own integrated commit, in order, and take the failing task out of the train. Each task still gets its own review. Never run two gates at once. `pgrep -f 'bin/chec[k]$|check(\.js)? ru[n]|check-bootstra[p]'` shows a running gate.
4. In Cafetera, merge, gate and land a train with one command from the primary checkout on the main branch: `./bin/land --merge BRANCH`, with one `--merge` for each approved branch (at most 3), the approved review reports, and the tasks to close. `./bin/land --help` gives its options and exit codes. Make it the whole background command and read its exit code. It rebuilds the installed CLI, runs the gate (`./bin/check` when the range touches `haxe_libraries/`, else `caf check run`), and then lands the train as step 9 says. To gate without landing, such as one task alone after a train failed, do the steps yourself. The installed CLI holds a compiled copy of the check plan. So first rebuild it from the integrated commit: run `PATH=$(dirname $(command -v lix)):$PATH ./bin/install-caf` in the checkout that the installed `caf` points to. Then run the gate as `caf check run` from that repository root, and read its exit code as the gate result. Make it the whole background command. You may redirect its output to a file, but never add `;`, `echo`, or a pipe, because then the shell reports a different exit code. Read the exit code in the completion notice. Each stage keeps its output and a Receipt under `build/caf/check/runs/`. Use `./bin/check` instead when the change touches `haxe_libraries/`, because only `./bin/check` runs `lix download`. Also use `./bin/check` when the installed CLI cannot be rebuilt from the gated commit, for example in a worktree whose commit the installed `caf` was not built from.
5. When the CLI bytes change, update every recorded CLI digest pin in the same change.
6. Commit with a Conventional Commit message. Land reviewed, gated work yourself: with `./bin/land` in Cafetera, `pnpm land` in Caffeine, and a plain `git push` in F12E. Until `pnpm land` exists (caffeine-g8z.35.14), land a Caffeine train with `pnpm check` on the merged main, then a plain `git push`, with nothing between. A range that touches approval-bearing paths (`caf/locks/**`, `caf/agents/**`, `caf/policies/**`, `scripts/hooks/**`, `.beads/hooks/**`) goes through the owner push prompt: run `caf push-approval-paths` as one plain command. An active owner push grant lets you push its in-scope paths yourself with `caf push-grant push origin master --review SHA256 --check-run TOKEN --task ID`, after one review by another model and a full gate; `caf situation` shows whether a grant is active. In Cafetera, `./bin/land` takes that grant route for such a range, and when the grant refuses, it stops and prints the owner route. Never force-push, deploy, or publish unless the owner asks.
7. After each merge, run `scripts/hooks/beads-export.sh sync`, then `caf graph set build`, so the graph and Caffeine see the new task comments and notes. `./bin/land` runs the export sync itself, before and after its closes. The `./bin/install-caf` run in step 4, which `./bin/land` also does, writes the generated `.claude/CLAUDE.md`, so the installed `caf` never lags the main branch.
8. Before handoff, verify the merged result once on the exact commit. Close the task with the commit, commands, and results written in a file. When the task changed source, the close reason also carries the stage line of `caf:concept:statement:cmlization:stage-line`. `./bin/land` does each close that you name, with the gate's run folder as evidence; without it, run `caf task close <id> --reason-file FILE --evidence build/caf/check/runs/TOKEN`. Each `--evidence` is the gate's run folder or a run or Receipt id. The command refuses a close without one, because `caf situation --full` counts only the close reason as evidence; a review verdict alone does not count.
9. Verified means landed (owner decision DB1, 2026-11-19). A change is verified when its review approves its exact commit and its gate passes on the merged commit. Then it lands at once. The land command runs the gate, and when the gate passes, it pushes the gated commit, closes each task of the train with the gate run, and ends each merged worktree: `./bin/land` in Cafetera (step 4), `pnpm land` in Caffeine. Only one commit may follow the gated commit: the task export refresh, which changes only `.beads/issues.jsonl`. When HEAD or the tree changed in another way during the gate, nothing is pushed. Where a land command is missing, do these steps yourself in that order, with nothing between the gate result and the push. Test each change in one step with three testers: the scripted walk decides, a persona adds findings, and the owner tests after the landing, except in the cases that the statement below names. A test result file has the line `Result: passed|failed|inconclusive COMMIT by TESTER`. It never starts with `Verdict:`, because that line marks a review. For trains (DB7), take what is approved when the heavy slot is free, at most 3, oldest first. Keep a compiler or dependency pin out of a train that the owner waits for. Land first: while an approved change waits for the heavy slot, start no new worker in its lane. When a product gate, such as Caffeine's, and a Cafetera gate both wait for the heavy slot, start the product gate first. After a merge, make the generated files again with the repository's own command. At each approval, run `git merge-tree` against the main branch to find conflicts. `caf describe caf:concept:statement:semantic-tree:task-start-worktree-lifecycle` gives the full rules and their exceptions. Record each train that you plan in Beads, such as one comment on each of its tasks with `caf task comment ID --file FILE`, not only in an evidence file: a plan that lives only in a file never runs (cafetera-1y1k.1). A measurement or a follow-up that does not block the review never holds back an approved, gated change. Record it as its own task instead. The daily integration limit still applies: work beyond it lands first on the next day. After each landing in Caffeine, restart the owner's test server from the new main branch (`caf:agentspec:rule:caffeine:dev-server-follows-main`).
10. Merge a pull request in an owner-maintained repository only under the conditions of `caf:agentspec:rule:dependency-integration-lifecycle`. Put `--repo` first: `gh pr merge --repo fullofcaffeine/<repo> <n> --squash`. The harness denies `--repo` after the number, such as `gh pr merge <n> --repo ...`, because gh lets a later `--repo` win. Give `--match-head-commit` the full 40-character head hash; a short hash fails. Never add `--admin`, `--delete-branch`, `-R`, or a pull request URL.

### Park what belongs to the owner

The owner wants report-only operation. Do every step that you can and may do yourself. Do not guess. One typed list, `AgentSpecOwnerReservedDecision` in the AgentSpec module, names the decisions that only the owner makes. The rule `caf:agentspec:rule:act-dont-ask` delivers it. The decisions are: accepting authority (approval records, policy or selection re-pins, pushes touching approval-bearing paths); an outward or irreversible effect the owner did not request (deploy, publish, pull requests outside owner-maintained repositories, cloud resources, deleting or overwriting others' work); a choice between meaningfully different outcomes that the request does not settle; a harness or permission refusal. When the work needs one of them, park it as a question (below) and continue with another eligible task. Use no other list of stops.

The list does not say the following, so apply it too:

- Accepting authority: prepare the approval record or the policy re-pin on a branch. Only the owner accepts it (`caf:agentspec:rule:owner-only-approval`). Never pass `--i-am-the-owner`. Push an approval-bearing range yourself only when an active owner push grant covers it (`caf push-grant push`, after one review by another model and a full gate).
- An outward effect: an effect that the owner requested is not reserved. For example, the owner asked for merges in the owner-maintained repositories, and `caf:agentspec:rule:dependency-integration-lifecycle` states the conditions. A license, a new repository, DNS, a credential change, and a change in any other repository that the loop does not attend stay with the owner.
- A meaningful choice: this includes scope, wording that the owner accepted, a P0 priority, a reorder of tasks, and a drifted copy. Set the first priority of a new task yourself, P1 to P3, from the priority table of `caf:concept:statement:independent-review:finding-intake`.
- A refusal: never work around it, and never edit harness settings such as `~/.claude/settings.json`. When the refusal blocks an effect that the owner requested, prepare the allow row or trust proposal in CML on a branch, record one task, and park the one owner act that applies it.

For each question, choose one route: ask now, park, or adopt the default. The route table `AgentSpecOwnerInputRouteRow`, beside the owner-reserved decision list in the AgentSpec module, records the route for each reserved decision and each risk of the default. It is reference data with tests; no command or loop step reads it yet, so apply it yourself with the rules below. A scope can add rows. The strictest route wins, and no scope lowers the floor.

- Wait, and never adopt a default, when the question is about accepting authority, an outward effect that the owner did not ask for, or a harness refusal; when the default makes a network, secret, publication, or destructive effect; when one revert cannot undo a wrong guess (a public contract, another repository, spending, a license, or deleted work); or when the default changes text that the owner accepted (a policy, an approval record, a P0, or the task order).
- Adopt the default at once when it is read-only or a local write, one revert undoes it, and a design review or a CML default names it. Write a decision note, and list the default when the owner returns. When nothing names the default, ask the design reviewer first. An intent or preference question without a reviewed default applies its read-only or local reversible default after 48 hours, but never while the owner is away. Then journal the adopted default, write one comment on Q that quotes this 48-hour rule, and close Q with a decision note that passes `--follow-up T`. An approval question and a question under the Wait rule above never take this path.
- Ask now only when waiting does harm or costs money, or when the owner is present and the question blocks the next task of the goal epic. When the owner is away, park the question instead and stop the affected work (`ownerAwayRoute`; see the section on owner away below). Silence never grants authority.

To park a question:

1. Search the open questions first with `bd list --label human`, which lists every task labeled `human` that is not closed (`bd human list --status=open` leaves out blocked and deferred ones). When one already asks the same thing, add your blocked task to it. At most 10 questions stay open; the 11th question stops the loop.
2. Create one Beads task Q with the label `human`, assigned to the owner. Give Q the priority of the highest-priority task that it blocks, but never P0, and the milestone label of that task. Write its description in a file, with one line for each of: Question (one exact question); Kind (approval, intent, or preference); Reserved because (the owner-reserved decision, and the risk of the default); Options (A, B, C); Default (the recommended option, and when it applies by itself); Blocks (the tasks that wait, and the work that continues); Evidence (the evidence ids, the date asked, and your agent role).
3. For each task T that waits for the answer, run `bd --actor <your agent id> dep add T --blocked-by Q`. Then `bd ready` skips T until Q closes. Release your claim on T (`bd --actor <your agent id> update T --status open --assignee ""`) with one comment that says how to resume. Journal it with `caf note --task T --kind question --text TEXT --ref Q`. Never use the `deferred` status or a hand-set `blocked` status for this, because `caf situation --full` flags both.

The owner reads one queue. `caf situation` prints `Waiting for the owner: N questions, M acts` ("acts unknown" until a pending-act list exists) with the first question and the ids of the next two, and `bd list --label human` lists them all. The owner answers in one of two ways: in chat, or with `bd human respond Q -r B`. For a chat answer to an intent or preference question, quote the owner's words in a comment on Q, and close Q. Then write `caf note --task <loop epic> --kind decision --follow-up T`. A question of kind approval is an owner act. It never times out. Neither a chat "yes" nor a `bd human respond` answer is the act: the owner still runs the act in their own terminal, and Q closes only on the Receipt or note of that run, never on a quoted answer. Never run `bd human respond` or `bd human dismiss` yourself. Close Q yourself only on the owner's quoted answer, on the Receipt or note of an approval act, or under the 48-hour rule above; that rule lets you close Q and nothing more.

Put all owner items into one message, with one exact command for each. Any text that names an owner act, such as an exact owner command, goes into a file first, never onto a shell line, because the guard hook refuses such text on a shell line. Then pass the file: `caf task comment <id> --file FILE`, `caf task close <id> --reason-file FILE --evidence RUN`, or `caf note --detail-file FILE` (a file inside the workspace). Reach the owner through the harness permission prompt where supported. Never freeze unrelated merges to keep an owner command applicable.

### While the owner is away (sleep mode)

The owner is away from the moment the owner says so, such as "I am going to sleep" or "activate sleep mode", until the owner clearly says that they are back, such as "I'm here". Only those return words end it: silence, time, or a chat message about other work never does. When it starts, write one note: `caf note --task <loop epic> --kind constraint --text "Owner away since T <owner time zone>, by the owner's words"`. When the owner returns, write a second constraint note that cites the first by its block id, such as `--ref caf:trace:note-block:workspace:cafetera:root:cafetera-yg3w:1200`, then send the morning report.

While the owner is away, keep doing goal-epic tasks, bug fixes, tests, follow-ups with an accepted design, and lane work with settled scope, with the normal reviews, gate train, and reviewed, gated pushes. Use the record's tighter away profile: `caf describe caf:agentspec:loop:cafetera-main` prints it under "While the owner is away". The record is compiled CML, so that page opens only in a Cafetera checkout after `caf compile run`; elsewhere, read `caf/workflows/CafeteraMainLoop.hx` in the Cafetera repository. It allows at most 6 integrations in the whole away period, counted across midnight, not 6 a day, and at most 1 second opinion in the whole away period, only for work that does not converge. Never ask now: park the question and stop the work it affects. Adopt a default only when a design review or a CML default names it, under the Adopt rule above. The 48-hour rule adopts nothing while the owner is away: those questions stay parked until the owner returns. Park every question under the Wait rule. Do not start design threads, and do not add modules, schemas, commands, ADRs, or concept renames beyond designs that the owner accepted. Do not clean up branches or worktrees, upgrade dependencies, or start scheduled sessions. The owner allowed two things while away, and the same page lists them under "Owner loosenings": a push under the owner push grant (`caf push-grant push`), and a merge in an owner-maintained repository under `caf:agentspec:rule:dependency-integration-lifecycle`. Also stop on a harness refusal, low free disk space, or a suspected secret leak or destructive mistake.

Write the morning report to an evidence file first, then send it as one message. It is the progress report of the section "Report progress on request", with each owner act given its exact command, and with one more part after the decisions: the defaults adopted while the owner was away, each with its revert commit and note id. Add the failed, parked, or stopped work, and the limits used.

### Report progress on request

When the owner asks how the work is going, write a progress report from four `caf` reads only. First, run `caf situation`. Second, run `caf timeline --since T --limit 1000 --json --kind note --kind note-correction --kind receipt --kind task-claimed --kind task-closed`. Third, run `caf task list --lane all --status in_progress`. Fourth, run `caf task ready --lane all`. T is the owner's local midnight in the time zone of the loop record, written as a UTC time, such as `2026-11-15T06:00:00Z`, because `--since today` means the UTC day. The owner can name another window. Then write at most 40 lines in this order: 1. a summary in three lines; 2. waiting for the owner: the acts, then the questions, each with your recommendation; 3. the decisions of the day, the owner's first; 4. the challenges and blockers; 5. the progress of each lane: closed (from the task-closed events), in progress, and next (from the ready list); 6. what you could not read, such as the task trackers of the compiler repositories. Give each number with the command that printed it. Copy no local path, email address, or private note title. Write no journal note for a report. The morning report is the same report plus the defaults adopted while the owner was away.

### Review deeply with the reviewer roles

Send architecture decisions and broad reviews to the design reviewer first. Before you send any review or second opinion, open `caf describe caf:concept:statement:independent-review:oracle-paused`: while that owner decision holds, it says which route each one uses. Add the second opinion when a case on the closed trigger list applies, or by judgement when one read is not enough, within the record's limit of second-opinion requests a day. The claim checker checks every load-bearing claim of a second-opinion report against current source before anyone acts on it. For every other review, the coordinator checks its load-bearing claims before acting, as the reconciliation statement says. `caf describe caf:concept:model:independent-review-v0` defines each role, names the model that fills it today, says what to do when a reviewer is not available, and says how to brief, store, and reconcile a review. Take in each finding as `caf describe caf:concept:statement:independent-review:finding-intake` says: re-check it, fix it in the task or find an open task first, and write one decision note for each finding.

### Coordinate a swarm

The loop has six roles: coordinator, worker, independent reviewer, design reviewer, second opinion, and claim checker. The independent-review concept defines each one, and only its current-bindings statement names the models that fill them. The coordinator owns task selection, integration, and every commit to the main branch. Give each worker exactly one claimed task, one isolated worktree, the exact inputs and acceptance, and a stopping condition (`caf:agentspec:rule:cafetera-agent:bounded-worker-delegation`). Before you write a worker brief, read `caf task brief ID`, or `bd show ID` plus `bd comments ID`. `bd show` alone leaves out comments, and owner re-scopes often live in a comment. Quote any owner re-scope into the brief word for word. Keep competing writers in separate worktrees, serialize integration, and gate the integrated result again. Every worker branch lives in its own worktree, never in the owner's primary checkout. Start each task with `caf task start ID` (add `--authority caffeine` for a Caffeine task) after `bd --actor <agent> update ID --claim`, never with `git worktree add -b`. It makes the branch `loop/<task id>` and the folder `.claude/worktrees/<task id>` from the origin default branch (owner decision WT1), refuses when either exists, and prints the Identity, branch, folder, and push lines for the brief. `caf describe caf:concept:statement:semantic-tree:task-start-worktree-lifecycle` gives every step from start to end, and the `Branches:` lines of `caf situation` name each branch that breaks it. The primary checkout stays on the default branch, and `caf situation` warns when it does not. After you create a worktree, or after a merge of the main branch that changes a lockfile, install dependencies there with the repository's locked install. In Caffeine, run `pnpm install --frozen-lockfile`, then `pnpm setup:backend`. Keep the swarm within the record's worker limit. Add a worker only when independent tasks make the total work cheaper or safer. Fill free worker slots with independent ready tasks, and batch approved branches into gate trains, within the loop record limits (`caf:agentspec:rule:cafetera-agent:bounded-worker-delegation`). A worker's report is evidence to verify, not acceptance. When you start any agent, pick its reasoning level as the current-bindings statement says (a level that the owner names always wins), pass that level as the Agent tool's effort on Claude Code, and state it in the brief's Identity field. A Claude Code session cannot change its own effort. Run a phase that needs a higher effort as a subagent, and recommend `/effort <level>` for the main session. The worker-handoff journal note names the agent id, the model, and the effort.

Write one short brief for each worker. A worker gets the guidance files but not the `caf situation` output, so the brief must carry the facts that can change. Use these eight fields:

- **Identity:** the agent id `<configured agent>:<role>-<task>`, where `<task>` is the task id without its prefix, such as `cafetera-agent:worker-0jpj.174` or `caffeine-agent:reviewer-3p4.4`; `caf task start` prints the worker id in this form, and the model and effort that you chose, with a one-line reason. After the colon, use only lowercase letters, digits, dots, and dashes, at most 64 characters; otherwise Caf records `unknown`. Caf records the id as a delegate of that agent, with that agent's authority and no more. The agent puts `BEADS_ACTOR=<id>` in front of each `caf` command and passes `bd --actor <id>` on each Beads write, because an export alone is lost (step 4 of Choose one task). In a checkout that its configured agent bound, a delegate needs no bind of its own: its `caf task` writes go through that binding.
- **Goal:** the task ID, the result that the worker must deliver, and when the worker must stop.
- **Write scope:** the one worktree and branch that the worker can change, as `caf task start` printed them (`.claude/worktrees/<task id>` on `loop/<task id>`), and the paths that it can only read.
- **Live constraints, with source:** each fact that can change, and where it came from, such as an owner re-scope or the free disk space, and how the worker can refresh it. While the owner is away, include the away note (its block id and text) and the away profile. Name the selected policy and WorkContext (the pinned rules and evidence for this work), or say that they are missing. Every brief also says: use fixtures only; never open or copy a real note store (`.caf/notes/`) or the owner's note files; stay out of the cases reserved for the counted proof runs. All agents of a session share one scratchpad, so every brief also says: write commit messages through stdin (`git commit -F -`) or a `mktemp` file, never a fixed file name in the shared scratchpad; keep scratch files in a subfolder named after the agent id with the colon replaced by a dash, such as `<scratchpad>/cafetera-agent-worker-0jpj.174/`.
- **Verified and assumed:** what you observed yourself, and what you only assumed. Tell the worker to verify each assumption within the permitted effects.
- **Permitted effects:** the exact checks and commands that the worker can run. The brief narrows what the worker can do and grants nothing new.
- **Owner-reserved acts:** the acts that the worker must not do and must report instead.
- **Output:** the commit, the files, the approval-bearing paths (step 6 of the review section) that each commit touches, or `none`, the commands with results, the deviations, the limits (what the worker did not check), and the open owner items. When the task changes source, the output also gives the stage line that `caf describe caf:concept:statement:cmlization:stage-line` defines. When the task adds code, the output also names the owning module, the joining pattern, and the reuse case of each new piece, as `caf describe caf:concept:statement:semantic-tree:module-fit` defines.

### Stop and report

Keep working while `bd ready` shows tasks that do not wait for a question. Stop on the record's stop list: when no eligible task remains, when two consecutive iterations fail the gate for the same reason, when everything left needs the owner, or when the integrated tasks of the owner's local date reach the effective daily limit. Also stop when an 11th question would open. End every iteration with two lines: what was done (commit and task) and what is next. End the last message of a loop with the owner queue: the owner acts to run; the questions by priority, then by how many tasks each blocks, then by age; and the defaults adopted while the owner was away. While a long gate runs, wait for its completion notification instead of polling.

Reason: An unattended loop is only safe when task choice, verification, commits, and owner decisions follow the same written rules in every harness and every iteration.

Examples:
- The gate fails twice for the same unrelated stage. Stop the loop and report the failing stage and its evidence instead of retrying.
- The owner asked for the calendar workstream. A ready calendar task is assigned to another agent that has not updated it in three days, and no session is working on it. Set yourself as its assignee with `bd update ID --assignee`, write one handoff comment, and write one journal note before you work on it.
- The ready list holds a P0 measurement task and a P1 task that needs a license approval. Take the measurement task, and record the license question in the other task's notes.
- Two independent tasks are ready. The coordinator gives each worker one task and one worktree, then integrates and gates the combined result before one commit at a time.

Limits:
- No claim that a worker's report is accepted work before the integrated gate passes.
- No push of an approval-bearing range, deploy, publication, pull request outside owner-maintained repositories, credential change, or destructive action without the owner.
- No takeover of a task another live session is updating.

Authority boundary: This skill organizes task selection, verification, and coordination. It grants no repository, task, provider, credential, publication, or effect authority beyond what the owner and each repository already allow.
